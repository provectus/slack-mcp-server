## 1. Feature Description Source

- **Source:** a `context/product/roadmap.md` item, a **GitHub issue**, prompt text, or a pre-generated spec. There is no dedicated ticket tracker, but the project's GitHub issues on `provectus/slack-mcp-server` are a valid feature/bug source.
- **Fetch transport:** direct file read (`context/product/roadmap.md`) for a roadmap item; `gh issue view <url-or-number> --repo provectus/slack-mcp-server --comments` for a GitHub issue (with the `github` MCP as fallback); the argument text itself for a prompt.
- **Normalization:** extract a short feature title and description. For a GitHub issue also keep the **issue number** and URL — there is no formal ticket state to transition, but the number lets the PR close the issue on merge (`Closes #N`). Work is otherwise keyed by the spec directory name (`SPEC_NAME`).
- **Pre-generated specs:** yes — a spec directory may already exist under `context/spec/`. Entry-point detection: glob `context/spec/*/`, and if one owns this feature, resume from the first missing artifact (skip `/awos:spec` if `functional-spec.md` exists, skip `/awos:tech` if `technical-considerations.md` exists, skip `/awos:tasks` if `tasks.md` exists). For a GitHub-issue source, resume-detection also checks whether the issue is already closed or a merged PR references it. With no argument, resume from the next incomplete roadmap item.

## 2. Git Flow

- **Base branch:** `master` on the `fork` remote (`provectus/slack-mcp-server`). Fetch it as `fork/master`; branch from and rebase onto it.
- **Branch naming:** `type/kebab-description`, mirroring the Conventional-Commit type — `feat/<slug>` for a feature, `fix/<slug>` for a bug, `docs/<slug>`, `style/<slug>`. Example: `feat/group-dm-support`, `fix/channels-refresh-counts-only`.
- **Submodules:** none.
- **Target sync & conflicts:** rebase the working branch onto `fork/master`. Checked twice — before opening the PR and again before merge, since upstream/`fork` may move while gates run. Conflicts are resolved by a subagent; non-trivial resolutions are confirmed with the user; the local gates (`make test`) re-run after any sync.
- **Worktrees:** main-repo-only. No worktree tooling exists (no `make worktree-init`, no `/worktree`), the project is a single-maintainer fork with no shared-resource contention that would force isolation, and a fresh worktree would only need `go mod download` — not worth the setup. Work happens on a branch in the main checkout.
- **Sanctioned verification path:** n/a — nothing shared blocks a run. The server binds `127.0.0.1:13080` only in SSE/HTTP transport mode; unit tests (`make test`) need no running service, and there is no always-on dev service reserving the port. Verification runs `make test` and, when a criterion needs a live render, builds the binary (`make build`) and drives it directly (stdio MCP handshake, or the SSE endpoint on a free port) — the agent stands this up itself; it is never handed to the user.

## 3. Repository Topology

- **Layout:** monorepo — single Go module `github.com/korotovsky/slack-mcp-server`, one working tree.
- **`context/` location & sharing:** `context/` is a plain directory inside this repo (not a symlink or submodule); it is always reachable.
- **Spec commits go to:** this repo, the working branch — `context/spec/{SPEC_NAME}/` is committed alongside the code.
- **Pre-flight check:** confirm `context/product/` and `context/spec/` exist and the working tree is on the intended branch before running any AWOS command.

## 4. Review

1. **Local static checks** — `make test` (`go test -count=1 -run=".*Unit.*" ./...`) must be green before committing. `go fmt ./...` is run to keep the diff formatted (it is mutating, not a gate). There is no `go vet`/`golangci-lint` in this project.
2. **Local AI review** — a dedicated reviewer subagent (independent of the orchestrator that implemented the change) reviews the diff against the spec, writes findings to `context/spec/{SPEC_NAME}/review.md`, and returns only the verdict, finding count, and path. Findings are presented to the user for a keep/drop decision; accepted ones are applied by a fresh agent before anything is pushed. No reviewer bot is configured on the code host, so this is the only AI review.
3. **GitHub CI on the PR** — opening a PR triggers `unit-tests.yaml` (`make deps` + `make test`) and `security-trivy.yaml` (Trivy filesystem scan, `severity: CRITICAL,HIGH`, `exit-code: 1` — fails the build on findings). The flow **waits for both and fixes failures in a loop**: diagnose from the failed job's logs via the `gha-diagnosis` skill, push, re-check until green.
4. **No automatic reviewer, no remote human review** — single maintainer; there is no CodeRabbit/Copilot config and no second reviewer.

- **Approval gates:** two — the flow stops after `/awos:spec` and again after `/awos:tech`, so each document is reviewed before the next is built. `tasks.md` gets no gate; `/awos:implement` starts right after `/awos:tasks`.
- **Change-request timing:** after local review — the PR opens only after `make test` and the local AI review pass, so CI minutes are spent only on reviewed code.
- **Max-wait & escalation:** CI is fast (Go unit tests + a Trivy scan, typically a few minutes). Size the `Monitor` timeout to ~10 minutes per poll window, poll interval 30s. On expiry, auto-relaunch the monitor once; past ~20 minutes with gates unsettled, stop waiting and ask the user.

## 5. Delivery

- **Mode:** batched. Features merge to `fork/master` as they finish; user-facing releases are cut separately and infrequently by tagging (`make release TAG=vX.Y.Z`), which batches merged work into an NPM/GitHub/Docker release. Releases are **out of the per-feature flow**.
- **Merge policy:** a human merges. The flow drives everything up to green gates, then **stops at the ready-to-merge state** and reports the PR link — the maintainer merges on GitHub. The flow never merges.
- **Post-merge CI:** pushing to `master` re-runs `unit-tests.yaml` and `security-trivy.yaml`. Because the flow hands off before merge, these are observed by the maintainer after they merge — not automated by the flow.
- **Approvals:** none beyond the maintainer's own merge.
- **Versioning:** git-tag driven, via ldflags (`GIT_VERSION = git describe --tags --always --dirty`). No VERSION file. Bumping happens only at release time (`make release`), not per feature.
- **Deployment:** never, per feature. Deployment is the tag-triggered release (`release.yaml` → NPM + GitHub release + DXT; `release-image.yaml` → multi-arch Docker to `ghcr.io`), run manually by tagging. The flow does not tag or deploy.
- **Ticket state transitions:** n/a — ticketless source.
- **Definition of Done:** the PR is merged into `fork/master` with green CI. Since the flow hands off at ready-to-merge, its terminal reported state is "PR open, all gates green, ready to merge"; the maintainer's merge closes the loop. The close-out reminds the maintainer to check off the corresponding `context/product/roadmap.md` item after merge.

## 8. Context Strategy

- **Mode:** single session with subagent-isolated stages. Chained headless sessions are not used (manual trigger, §6).
- **Stages isolated in subagents:** the **fetch** stage (mechanical read / `gh issue view`), the **CI-failure diagnosis-and-fix** work (delegated to `gha-diagnosis` / a specialist subagent from the failed-job logs), the **local-review** reviewer (a dedicated independent subagent), and **conflict resolution** during a rebase. Each returns a terse report — paths, verdicts, counts — never full content.
- **Stages kept in the main context:** the entire AWOS chain — `/awos:spec`, `/awos:tech`, `/awos:tasks`, `/awos:implement`, `/awos:verify`. Determined at generation time by inspecting `.awos/commands/*.md`: `spec`, `tech`, `tasks`, and `verify` all use `AskUserQuestion` (they interview the user, and subagents cannot reach the human); `tech`, `tasks`, and `implement` dispatch their own subagents (agents do not nest). Every one of the five therefore must stay in the main context. The orchestrator also stays in main for the approval gates, keep/drop decisions, and the merge hand-off.
- **Flow log:** `context/spec/{SPEC_NAME}/flow-log.md` for the feature command (logging starts once the specs stage creates the spec directory); `context/fix-log-{BUG_ID}.md` for the bug-fix command (known from the fetch stage on). The flow's resumable memory — a fresh session resumes by reading this one small file. Committed with the work and finalized at commit-push: once the PR is open, the flow stops writing to the tracked log and reports late-stage progress instead.
- **Model tiers:** the fast/cheap tier for mechanical transport work — fetch, resume-detection checks, first-pass CI-log triage. The strongest available tier for judgment — implementation, diagnosis, the local AI review, `/awos:verify` evidence gathering, and conflict resolution. Tiers, not model names.

## 9. Notifications

- **Channel:** none (interactive runs only). The flow is attended — two approval gates and a human merge — so the maintainer is already watching. Progress is reported inline.
- **Announce on:** n/a.

## Bug-fix Flow

- **Generated:** yes — `/fix-bug` → `.claude/commands/fix-bug.md`.
- **Bug source:** a plain description (the command argument) or a GitHub issue URL (fetched via `gh issue view`). No crash-reporting tool (Crashlytics/Sentry) is used, so there is no stack symbolication step.
- **Classification & amendment policy:** every fix is classified — **conformance** (code violated a correct spec → fix + regression test, no spec change) vs. **divergence** (spec was wrong or behavior intentionally changed → fix + regression test + amend the owning `functional-spec.md` via `/awos:spec` update mode, after user confirmation). A bug mapping to no owning spec (legacy/cross-cutting) proceeds without amendment.
- **Regression-test expectation:** a fix adds one failing→passing Go unit test (`testify`, run by `make test`) capturing the bug, honoring the `<!-- skip-tests: true -->` opt-out if the owning `tasks.md` carries it.
